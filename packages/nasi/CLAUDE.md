# @kaja/nasi

The agent brain: OpenAI-compatible tool loop, the store interface (sessions as message and tool-call rows, memory, datasets; hosts implement it over SQLite or Postgres), built-in tools, and `Nasi`, the cloud turn wrapper the API uses.

Hosts (full CLI, API) construct it and pass a store, model client, prompt context, and `includeLocalTools`. This package has no Ink, Hono, Better Auth, sqlite, or pg.

## Commands

```bash
bun run --filter @kaja/nasi test
```

## Layout

```
src/
  index.ts           # public API
  nasi.ts            # Nasi: the cloud turn (open a session, run, pause and resume, close)
  personas.ts        # dataset loaders the host registers (setDatasetLoaders, loadDataset)
  warn.ts            # warn + setWarnHandler
  agent/             # Agent, run(), system prompt, compaction, command risk, telemetry
  store/             # NasiStore interface + in-memory adapter; images.ts (SessionImages over the host's ObjectStore plus its ImageRows: SQL in the stores, `memoryImageRows` here); rows.ts splits a session into message/tool-call rows and joins it back
  models/            # OpenAI client factory (no singleton)
  tools/             # builtin tools + createTools({ includeLocalTools })
  mcp/               # connectMcpServer; launch.ts resolveLaunch (a stdio manifest's package → the runner this host has)
  abilities/         # AbilityStore, folder store, loadAbilities, load_skill, HTTP tool executor, MCP ability targets, code tools
  client/            # `@kaja/nasi/client`, the TUI's cloud mode: info(), compact(), turn(), turn_stream() SSE (no store / loop)
  security/          # SSRF guard (the path guard is tools/path-guard.ts)
```

## Conventions

- No reads of `settings.toml`; hosts inject store, model client, prompt context. Parameterized SQL only; session ids are UUIDv7 text. Do not log prompts, memory content, or API keys.
- Recoverable problems (a skipped ability, a missing key, a failed MCP connect) go through `warn`; hosts route them with `setWarnHandler`, silent until they do.
- `includeLocalTools` (default false): files, shell, MCP. Code tools (an ability's `tool.ts`) come only from a store on the user's machine (`AbilityStore.listCodeTools`), and `loadAbilities` imports only the ones a persona lists.
- The system prompt is built when a conversation starts; `refreshAbilitiesInPrompt` (every turn, in `run`) rebuilds it only when the `## Skills`, `## Personas` or a sticky `## Skill: <name>` section no longer matches, so changes reach running conversations without breaking prompt caching.
- `run_command` runs without asking only when `isSafeCommand` (`agent/command-risk.ts`) says so: a whole-command match on `Agent.safeCommands` (the TUI's `commands.toml`, else `DEFAULT_SAFE_COMMANDS`), no shell metacharacters, not `isDangerousCommand`, no path segment `secrets.toml` or `.ssh`. The model's `mutates` flag is only a hint. `runShellCommand` keeps 64 KiB of each stream and kills the child past that or after 15 s; child processes register with `trackProcess` so `killTrackedProcesses` can stop them on quit.
- Built-in tools declare arguments as a zod `schema` in `tool()`; its JSON Schema is what the model is sent (unless `parameters` spells it out), and `run()`/`runApprovedTool` check arguments with `checkToolArgs`, answering `Invalid arguments for <tool>: …` on failure. Tools with an outside JSON Schema (MCP, HTTP abilities, code tools) pass `parameters` only.
- A tool that throws (or isn't found) never aborts the turn: `run()` answers its call with `Error: <message>` and records status `error`. The run stops after three rounds in a row where every call failed (`MAX_FAILING_TOOL_ROUNDS`).
- Every tool goes through `mergeTools` (`tools/registry.ts`): one namespace, each tool stamped `origin` (`official` built-ins, `community` abilities) + `source`. Official names are reserved; other clashes keep the first and land in `skipped`. Host tools come in through `createTools`' `extraTools`, never appended afterwards.
- Telemetry: `run()` records each model round (`StepStat`) and each tool call (`CallStat`) on `session.telemetry`; a host that answers a paused call itself calls `recordPausedCall` first. A store writes telemetry beside the rows it saves and then clears it (`clearTelemetry`). A call's status stays unset when a person answered it; a client tool's is what the client reports (one it didn't answer is `skipped`).
- `ask_user` takes optional `options` (2 to 6 short strings): shortcuts a client may show beside the question, the human still free to write anything, and the picked text comes back as the plain answer. They ride on the `ask_user` event/step; options that don't fit the schema go back to the model as a failed call (no pause). `ASK_USER_OPTIONS_INSTRUCTION` tells the model the question must read fine without them, since not every client shows them yet (the terminal and both Telegram bots do). The event carries the pending call's `id`, and `pendingQuestionOptions(session)` reads a waiting question's options back off the saved call, so a host can check a later tap against the session alone.

## Approvals

A tool may set `approval(args)`: when it returns a summary, `run()` pauses with `confirm_tool` (`session.pendingToolApprovalId`) instead of executing, and the host runs it via `runApprovedTool` once the human approves (same shape as run_command's `confirm_command`; non-GET HTTP tools use it). Over `Nasi` the next turn's `approval: "approve" | "decline"` answers it: Nasi runs the call the session saved (`pendingToolCall`), never one the client describes, and a plain message skips it. `approve_session` adds the tool's allow key (`<source>:<name>`, `agent/tool-allow.ts`) to `session.grantedTools`, and `run()` skips the pause for matching tools. `NasiOpenOptions.abilityKey` hands abilities their keys; `NasiOpenOptions.egress(ability?)` hands out the senders requests go through (`egress()` for `fetch_url`, as `deps.fetchSend`; unset connects from this host, and a cloud turn then has no `fetch_url`).

## Personas and abilities

- Abilities come from a host-provided `AbilityStore` (`createFolderAbilityStore` for the CLI); `loadAbilities` returns extra tools the host appends. A broken ability is skipped with a warning, never thrown. With `warnUnknown` (the CLI), a persona entry naming an unknown ability or `tools` name gets a warning; the cloud leaves it off, since its store leaves out parts it can't run.
- Personas fix the tools: `personaTools` (`agent/persona-tools.ts`, over `abilities/persona-scope.ts`'s `toolsForPersona`) is what each round sends and runs. Builtins always, except the opt-in ones (`OPT_IN_BUILTINS`: `fetch_url`, `generate_image`, `edit_image` as `fetch-url` etc.), which a persona with an `abilities` list gets only by listing them (`personaGetsBuiltin`; the API's info route filters with it too); an ability's tools only when the active persona's `abilities` lists it (narrowed by an entry's `tools`); `load_skill` only with a skill in `load` mode. An agent without a persona gets every tool. `run()` recomputes per round, so `switch_persona` changes the next round's list; a call to another persona's tool gets a reason, not "unknown tool". A `sticky` skill's body is its own `## Skill: <name>` prompt section.
- MCP abilities connect lazily where the host asks (`createTools`' `lazyMcpAbilities`, used by `Nasi` and the TUI; the doctor connects all): `ensureAbilities(names)` connects the ones not tried yet, and `Agent.ensureTools` is how `run()` (`syncPersonaTools`, at turn start and in `applyPersonaToMessages`) asks for the active persona's, or all with no persona. They connect in parallel, each with a timeout (`mcpConnectTimeoutMs`, default 10 s).
- `connectMcpServer` takes `transport` (http/sse), an `allow` list and `approval` (never/writes/always; `writes` uses the tool's `readOnlyHint`). In the cloud (`includeLocalTools` false) every MCP ability connects over HTTP with `mcpFetch(name)`, a stdio one at the sandbox (`sandboxedMcpTarget`, its origin's requests going to `mcpSandbox.fetch`); `Nasi` passes `createGuardedFetch` (`security/ssrf.ts`: every hop checked, same-origin redirects only, bodies streamed, sent through `egress(name)` when set), with results capped and raw images over 10 MiB dropped. `Nasi.close()` shuts them.
- A stdio manifest names a `package` (`npm`/`pypi`/`docker`) or a `command`; `resolveLaunch` (`mcp/launch.ts`, via `mcpAbilityTarget`) picks how to start it here: npm on the host's own bun (`BUN_BE_BUN=1 <execPath> x <pkg>`, which uses Node when installed), else npx/pnpm dlx; pypi through uvx/pipx; docker last (`run -i --rm --init`, env by name). Nothing installed → `McpRunnerMissingError`, and `loadAbilities` leaves the ability out (`missingRunners`, reported only for persona-used ones). `requires = ["chrome"]` is met by Chrome stable or a Chromium (`findChrome`), passed as `--executablePath`. The cloud never resolves: `sandboxedMcpTarget` sends no command.
- **Roots**: a manifest with `roots = true` takes folders from personas (an entry's `roots`, expanded by `mcp/roots.ts`'s `expandRoots`: `~`, absolute, existing folders only). `loadAbilities` puts them on the target by persona id (none anywhere → left out, `missingRoots`); docker mounts all of them at their own paths. `connectMcpServer`'s `roots` declares the capability and answers `roots/list`; `createTools`' `ensureAbilities(names, personaId)` sets the persona's folders, sends `roots/list_changed` when they change and waits for the server to ask again plus `ROOTS_SETTLE_MS` (MCP has no ack), and leaves the server unstarted and its tools out for a persona with none. `Agent.ensureTools` gets the persona id from `syncPersonaTools`.
  - Read-only roots (`{ path, readOnly = true }`) need the manifest's `pathArgs`: `connectMcpServer`'s `refuse` (`readOnlyRefusal`: real paths, the nearest root decides, relative paths refused) stops a call that may write before it asks or runs; tools carry `readOnly` so an all-read-only persona gets no writing tools; docker mounts a folder `readonly` when every persona does.
  - Backed-up roots (`backup = true`, also via `pathArgs`) with `createTools`' `backupDir` (local only): `beforeWrite` copies each existing named path to `<backupDir>/<path>/<time>` (`backupFiles`, never pruned; a failed copy stops the call), and `tools/builtin/backups.ts`' `list_backups`/`restore_backup` join the first backed-up server's tools, only for a persona with a backed-up folder there.

## Client tools (a cloud turn's terminal)

`NasiOpenOptions.client` (`abilities/client.ts`'s `NasiClient`) declares the tools and skills the client runs on the user's computer, each turn. `clientToolGroups` makes stubs with `Tool.runsOnClient` (an ability's carry its source so personas pick them; builtins like read_file/run_command are official), `withClientAbilities` hides the store's own copy of every ability the client declares and lists the client's skills (a sticky one's `body` for the prompt), and load_skill's `clientSkills` hands those to the client. `run()` collects a round's client calls after running the rest, answers any ask/confirm/approval in the same round as "not now", and pauses with `client_tool_calls` (`session.pendingClientCalls`, status `needs_client_tool`). The next turn's `toolResults` are pushed by `answerClientCalls` (missing ones as `CLIENT_GONE`, images as one user message after), and `run()` with no prompt carries on. The store keeps them as one `client_tools` pause; joining finds the last assistant message's unanswered calls.

## Images

- Normalised and stored where they arrive (`images/normalize.ts`'s `normalizeImage`, on `Bun.Image`: at most 1568 px a side, EXIF dropped, a PNG stays PNG, a GIF or transparent WebP becomes one, the rest JPEG q85; an already-normalised one passes through), then `agent/images.ts`'s `storeImage` into `NasiStore.images(session.id)`; no other copy is kept. Sources: a tool's images in `run()` (`ToolResult.images` are bytes, never temp files), the prompt's images, a client's results (`answerClientCalls`). One that can't be used becomes a note for the model.
- Messages hold `kaja-image:<id>` refs; `resolveImageRefs` swaps in the bytes of the ones still in the request (after `withoutOldImages`) right before the provider call, so loading a session reads no image. Sessions get their id from `createSession()` so images have a home before the first save; a session without one keeps them inline. A new session whose turn fails before it's saved clears its images (`Nasi`).
- Each image's message carries a label (`agent/describe.ts`'s `imageLabel`: `[Image kaja-image:<id> (W×H): <text>]`) that starts as the source's alt; `Agent.describer` (the `vision` task's model) replaces it in the background with a short English description (kept in the image's row, reused for the same image). `seesImages(agent)` (the chat model's models.toml `images = false` says no; the cloud's model row has an `images` column): a model that can't see gets labels only (`withoutImageParts`) and waits for descriptions (`applyDescriptions`) before each round and at the turn's end; one that sees doesn't wait, and a late description goes in on the next turn. Images before `KEEP_IMAGE_TURNS` keep only their labels. A persona's `models.vision` pin replaces the describer (`applyVisionPin`).
- Events: `tool_image` carries `{ ref, key?, mimeType, alt }` (hosts show `key`'s object), `image_described { ref, description }` follows when a description lands. `run()` places `kaja-image:` links in `message`/`final`/`ask_user` events (`SessionImages.location`: a public URL in the cloud, a file locally; the session keeps the refs). `runApprovedTool` returns `{ text, images }`, each image labelled by the tool's text, and hosts pass them to `run()`, which yields a `tool_image` for each; any other prompt image is "an image the user sent".
- A reply's `![alt](https://…)` images are stored too (`storeRemoteImages`, before the reply joins the session): fetched like `fetch_url` would (so only where the agent has that tool, through `deps.fetchSend` in the cloud), normalised, and the link swapped for `kaja-image:<id>`, so a host only ever shows the stored copy; a link that can't be fetched or used stays as written.
- A `## Images` prompt section (with view_image) tells the model its images' labels, that view_image takes their links, that a tool's image is already on screen, and that `![…](kaja-image:<id>)` in a reply shows one again.
- `view_image` takes a `kaja-image:` link (`ToolContext.images`; the cloud's is `viewLinkedImageTool`, and a computer's declared view_image runs links here, paths there via `clientToolGroups`), asks first (`approval`) for a path outside the workspace (`resolveWorkspacePath`), and never reads secrets.toml or the store. `fetch_url` returns a page as Markdown (turndown over Readability's article, or the whole body less chrome without a real article or with `whole_page`; images and link URLs only when asked) and an image URL as a tool image. `edit_image` (`Bun.Image`, one pass per step to keep order: resize, 90° rotate, flip, brightness, greyscale; opt-in, cloud-safe) turns a `kaja-image:` link plus steps into a new tool image.

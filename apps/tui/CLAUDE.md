# @kaja/tui

Terminal chat with personas, tools, optional mic dictation, optional TTS, MCP, and Telegram.

This package uses Bun. The entry point is **`cli.ts`** at the package root (not `src/`).

## Commands

```bash
bun dev:tui               # from the monorepo root: interactive, attaches your real TTY
bun run --filter @kaja/tui test
bun session list          # from the monorepo root: local terminal sessions, newest first
bun session dump <id>     # one session as markdown with a Mermaid sequenceDiagram (id may be a unique prefix)
```

`bun session` (`scripts/session.ts`, tested in `tests/scripts/session.test.ts`) is a read-only debugging dump of `memory.sqlite`: it never creates or migrates the database, and it only sees terminal sessions (empty owner), not cloud or Telegram ones. Redirect `dump` to a file and open it in a Mermaid-aware viewer.

`memory.sqlite` is `@kaja/nasi`'s `createSqlStore` over a `Bun.SQL` SQLite client (`lib/store/sqlite.ts`'s `openLocalDb`: WAL, foreign keys on, `SQLITE_SCHEMA` applied): the cloud's `nasi_*` tables and columns, every row under `LOCAL_USER_ID`, sessions on the `local` channel. Every write goes through `sql.begin`, since on SQLite a plain query would run inside another save's open transaction. A file from before those tables (a `sessions` table, no `nasi_session`) is renamed to `<file>.legacy` with its `-wal`/`-shm`, never converted or deleted.

`bun run --filter @kaja/tui start` runs through Bun's workspace script runner, which does not pass the TTY through: Ink sees `process.stdin.isTTY` as falsy (skips the setup wizard, and the main app crashes with "Raw mode is not supported"). Use `bun dev:tui` (or `cd apps/tui && bun run cli.ts`) for interactive use.

## Modes

- **Resolved in one place**, `lib/config/mode.ts`'s `resolveMode` (used by `cli.ts` and `subcommands/abilities.tsx`): an explicit `--cloud`/`--local` flag, else settings.toml's `preferences.mode` (written by the wizard), else the legacy guess for configs predating that field (a usable chat model means local). The stored preference is what stops "Skip — I'll set up models.toml myself" from silently sending the next launch to cloud login. No config at all: the setup wizard asks.
- **Cloud**: no local agent, sqlite, MCP or shell tools; talks to `<apiUrl>/nasi/*` over SSE. Auth is a device login on first run; the single bearer token lives in the OS credential store via `Bun.secrets` (`service: "kaja-tui"`, `kaja-tui-<profile>` under `KAJA_PROFILE`; `name: "token"`), no credentials file. If the keychain is unavailable the CLI errors out and recommends `--local`. One cloud account at a time; `kaja logout` clears it. First run writes a minimal settings.toml (`createCloud()`: just `preferences.locale`, detected from the system, else `en-GB`). Cloud-only code: `lib/auth/`, `hooks/use-cloud-agent.ts`, `subcommands/run-cloud.tsx`.
- **Local**: agent logic lives in `@kaja/nasi`; this app is the host plus Ink UI, and requires a configured `models.toml` (your own provider, no silent fallback to cloud free chat; `subcommands/run.tsx` exits with an error instead).
- `components/layout/app.tsx` is the one TUI for both: `App` dispatches on `mode` to a thin `LocalApp`/`CloudApp` (driving `useAgent`/`useCloudAgent`), both rendering the same `Header`/`ChatViewport`/`UserInput`/`PersonaPicker` chrome. The `run_command` confirm is local-only.
- Personas: in cloud mode the user's cloud personas drive both `switch_persona` (model-invoked; `use-cloud-agent.ts` follows the `persona_switch` event) and the picker (Alt+P). A manually picked persona is session-only in both modes.
- Language always comes from settings.toml, set once at startup by `lib/cli/bootstrap.ts`'s `detectAndSetLanguage` (no `--lang` flag).
- The app never writes `~/.config/kaja/*.toml` at runtime; only first-run setup and the explicit `kaja config wizard`/`kaja config fetch`/`kaja config hooks` do (`fetch` backs up the previous file as `models.bak.toml`, `models.bak.2.toml`, … via `lib/config/fetch.ts`'s `writeTemplateConfig`).
- Quitting kills every tracked child process (`installShutdownHandlers` in `lib/cli/headless.ts`).

## UI

- No `/` slash-command menu. thinking, toolDisplay and voice are read once from settings.toml at startup (edit and restart). `toolDisplay`: `minimal` (default; `lib/tool-summary.ts` folds each finished turn's calls into one line, `Activity` shows the call in flight), `verbose` (a row per call) or `corner` (header spinner only).
- **Key bar** (`components/layout/key-bar.tsx`) is pinned to the bottom. On a narrow terminal `fitKeyBarItems` first swaps each hotkey's modifier, whichever it is, for `‽+` (`short` on the entry; the help modal names the real one), then drops the `droppable` PgUp/PgDn entries. Entries and hotkeys come from one `KeyBinding` list in `app.tsx`, so an entry that isn't shown has no live hotkey: modifier+L (help modal), +P (persona picker modal), +R (copy the latest message, via `uiEvents` "copy"), +E (expand code, only while a mounted block is longer than `codePreviewLines`), +O (the command or request an approval waits on, in a modal; only while one is pending). Modifier-less PgUp/PgDn entries scroll the chat a page (via `uiEvents` "pageUp"/"pageDown"; click only, the keys themselves are the hotkeys). Typing in the input emits "follow", which jumps the chat back to the latest message. The Esc entry is context-aware (`bottomChromeKey`): Quit while typing or while a command runs (`hooks/use-quit-guard.ts`: the first press only arms it), Close while a modal is open, Decline in a confirm prompt. Entries with an `onPress` are mouse buttons: `useMouseTracking` turns on button-less motion reports (mode 1003) and `key-bar.tsx` hit-tests each item's `useBoxMetrics` rectangle against `parseMouse` events.
- Why those letters: "R" not "C" because plain Ctrl+C is reserved globally by Ink to quit and is checked before any `useInput` handler; "L" not "H" because Ctrl+H is byte-identical to Backspace. The modifier is `preferences.hotkeyModifier` (`"alt"` default, `"ctrl"`, `"meta"`, or a pair: `"ctrl+alt"`, `"ctrl+meta"`, `"alt+meta"`) because no single key is universal: Alt types special characters on macOS terminals without "Option as Meta", Ctrl+letter collides with host shortcuts (VS Code's terminal), and a window manager can grab a combo before the terminal sees it (Ctrl+Alt+letter on some tiling WMs). Alt is Ink's `key.meta`; "meta" is the Super key, `key.super`, which only arrives with the kitty keyboard protocol (on, `auto`, in `run.tsx`/`run-cloud.tsx`). F-keys and Ctrl+digit were tried and dropped (Ink's `Key` has no F-keys; terminals don't send Ctrl+digit reliably). Hotkeys bind through `hooks/use-modifier-keys.ts`, whose `useModifierHeld` lights the entries up (`lit`) while every key of the modifier is held. Held keys count from each modifier key's own press/release and from a report's modifier field (terminals disagree on which they get right), so the order the keys go down in doesn't matter; "meta" is the Super key or the protocol's Meta. That needs the kitty keyboard protocol's release events and bare-modifier reports (`KITTY_KEYBOARD` in `lib/terminal-input.ts`, passed by `run.tsx`/`run-cloud.tsx`), which also makes every key arrive as an escape code with a release: so key handlers use `hooks/use-key.ts`'s `useKey`, which drops releases, instead of Ink's `useInput`. Shift+Enter (newline; needs the protocol, a plain terminal sends the same byte as Enter) is a separate binding in `text-input.tsx`, which `mutateTextForKey` keeps out of typed text.
- **Modals** (`components/elem/modal.tsx`): `App` wraps the chat in `ModalHost`; `Chrome` puts the screen in `Backdrop` and mounts a `<Modal title onClose>` beside it only while it is open (`modal` state in `app.tsx`: `"help"` → `help-modal.tsx`, `"persona"` → `persona-picker.tsx`, `"command"` → `command-modal.tsx`; add a name there for the next one). While one is mounted the host sets `InputBlockedContext`, so `useKey` goes inactive everywhere outside the modal (the modal re-provides `false` for its own subtree, so a menu inside works as usual) and the mouse consumers (`key-bar.tsx`, the chat's wheel, `useClick`) turn their `useTerminalReports` off; reports that aren't input (focus, colour scheme, modifier state) stay on. A new input hook must go through `useKey` (or check `useInputBlocked`) to respect this. A modal's own key handling therefore lives in a component rendered inside `<Modal>` (`DocsKey` in `help-modal.tsx`), never in the component that renders the `<Modal>`, which is still blocked. `Backdrop` is a raw `ink-box` with `internal_transform` (Ink's `Box` can't take one, but applies a box's transform to every text under it) that strips each line's colours and repaints it pale; box backgrounds aren't text, so tinted bands stay. It also blanks emoji to spaces of Ink's width (`paleLine`): a terminal that draws an emoji narrower than Ink counts it shifts the rest of that row, which showed as the modal's edge jutting out on that row. Esc, or a click on the "Esc Close" footer, calls `onClose`, so a `SelectMenu` inside leaves its own `onClose` out.
- Mouse, focus and colour-scheme reports come through `hooks/use-terminal-reports.ts` (a raw stdin `data` listener beside Ink's reader), not `useInput`: Ink 8 drops control sequences it has no key for.
- Code blocks show `codePreviewLines` (default 5) lines until expanded (`components/elem/code-preview.tsx`). An approval's command is never in the chat (it can be long): `ConfirmCommand` holds the question, and `CommandModal` (modifier+O) shows the command.
- **Prompts** (`components/layout/prompt.tsx`): a `PromptSpec` (title, options, placeholder) shown in place of the chat input as a list over the usual `UserInput`. The list has the keys while the field is empty; typing hands them to the field (the list dims), Esc empties it and gives them back, Esc on the list dismisses. A result is an option's id or the written text. `ConfirmCommand` is its approval adapter: text declines the call and tells the agent why (`notApprovedPrompt`; in the cloud a plain message, which the server takes as a skipped call). More option kinds join `PromptOption`. The agent's `ask_user` with `options` is its other use: the options sit over the field in the power border (an approval keeps the plain one; no title, the question is in the chat), a pick sends its text and typed text is sent as is. Esc empties typed text there and quits only from the empty list (`quittable` in `app.tsx`); `mic` is kept by `Chrome` so dictation survives the field being swapped for the prompt. A question without options stays the plain `UserInput` with an answer placeholder. The local Telegram bot shows the options as inline buttons too (`answerQuestion` in `lib/telegram/driver.ts`, same callback format as the cloud bot): a tap edits the message to `<question> → <option>` and runs a turn with the option as the user's text.
- **Theme**: `preferences.theme` (`auto` default, `dark`, `light`, `terminal`). `components/theme.tsx` holds every colour. A theme is a `Scheme` (foreground, background, accent, six hues, gray); `paletteFrom` derives the `Palette` (a colour per role, and `tint(hue, amount)` for every tinted background). Each palette becomes one @inkjs/ui theme, with Kaja's styles as a custom `Kaja` component read through `useKajaTheme()` (`usePalette()` for raw colours). No component names a colour itself: add a palette role or a style instead, never a scheme entry. A nested `ThemeProvider` must extend the surrounding theme, not `defaultTheme`.
  - Output outside the chat uses the _console theme_ (`consoleTheme()` in `lib/terminal-background.ts`; `kaja doctor` and `kaja abilities` call `resolveConsoleTheme()` first). Standalone Ink renders wrap themselves in `<ConsoleTheme>`, plain `console.log` lines use `paint(consolePalette().danger)` etc.
  - `auto` is resolved by `resolveTheme` in `run.tsx`/`run-cloud.tsx` **before** Ink renders, since it reads stdin: an OSC 11 background query followed by DA1 (every terminal answers DA1, so an unanswered OSC 11 ends early), then `COLORFGBG`, then dark. The same query asks the foreground (OSC 10) and the 16 ANSI colours (OSC 4) for the `terminal` theme, whose tints are fixed at startup. In the chat, `hooks/use-theme.ts` follows the terminal's colour-scheme reports (DECSET 2031) while the preference is `auto`; re-asking OSC 11 mid-chat isn't done because Ink splits the reply into pieces that would be typed into the input.
- **Markdown** (`components/elem/markdown.tsx`) renders block by block: `lib/markdown/blocks.ts`'s `splitBlocks` cuts at blank lines (never inside a fence, before an indented line or between items of one list) and caches each block's ANSI output, so a streaming reply re-renders only its last block. `tests/lib/markdown/blocks.test.ts` checks block-by-block output equals whole-text output; add a sample when the splitter learns a case. A code block with no language isn't highlighted (cli-highlight's guess costs ~17 ms a block). Tables are drawn by `lib/markdown/table.ts` and fit the terminal width.
- **Images**: a tool image is an `ImageRow` (half-block picture, its alt text replaced live by its description on `image_described`, where it came from (the `tool_image` event's `source`: a URL's site as an OSC 8 link, else the file's name; `lib/image/source.ts`), and "↗ open"). A click (`use-click.ts`) opens the stored picture (file locally, public URL in the cloud) with the `open` package; when nothing could, the OSC 8 link shows. A reply's `![…](kaja-image:<id>)` arrives placed by nasi; one not placed yet (still streaming) shows as alt text. The local Telegram bot sends a tool image with its alt text as caption, edits it to the description (`TelegramSender.editCaption`, latest 32 photos, since a description can land a turn later), and sends a reply's placed images as the stored files (an extensionless path is allowed only inside the images folder).
- A drawn picture is cached by source and size (`lib/image/render-terminal-image.ts`), **not** kept in the row's state: the scroll view (`virtual-scroll.tsx`) unmounts rows that scroll out of view, and a row returning without its picture measures its alt text instead, which scrolls the chat, which unmounts it again, so the picture flickers over a viewport that never settles (`tests/components/chat-viewport-image.test.tsx`). Failures aren't cached.
- **Copying a reply**: an agent message/question block (`CopyableBlock` in `components/elem/copyable-block.tsx`) highlights on hover and copies its own text (`lib/copy.ts`'s `copyToClipboard`) on click, same as the key bar's Copy button (`<modifier>+R`), which always copies the latest one instead.
- **Ink is patched** (`patches/ink@8.0.0.patch`, root `patchedDependencies`): its word wrap drops the space a soft-wrapped row would start with (`tests/components/text-wrap.test.tsx`). Bumping Ink means redoing the patch (`bun patch ink`, edit `build/wrap-text.js`, `bun patch --commit node_modules/ink`) or dropping it if upstream fixed it.
- **Hooks**: optional `hooks.toml` in the config dir (`lib/config/hooks.ts`), written by `kaja config hooks` (`lib/hooks/offer.ts`, also run by the wizard before its cloud/local split) and otherwise hand-edited; no file means silence, including no sounds. Each event (`HooksFileSchema`: message, question, confirm, reasoning, tool_call, notice, persona_switch, error, copy, login_code) is a list of `{ run, cancel? }` shell commands, all started at once and unref'd so they outlive a quit, with the text in `$KAJA_TEXT` and on stdin, plus `$KAJA_TITLE`, `$KAJA_SOUNDS`, `$KAJA_LOCALE` (the active language, so generated speech commands carry no hard-coded voice) and `$KAJA_HOOK`. `cancel` (true = this command, a string = a named group) stops the earlier run with that key first, in its own process group. `fireHook(name, event)` is the one entry point: `hooks/use-hooks.ts` (called from `Chrome` in `app.tsx`; `hookFor` maps timeline events, `message`/`final` and a `?`-ending reply are `message`, an `ask_user` from the tool is `question`), `switchPersona`, the copy action and the device login all call it. Events present on mount (a resumed session) don't fire. Not in the Telegram bot.
- **Sounds and notifications are system utilities**, no npm packages: `lib/hooks/detect.ts` finds a player / notifier / speech tool per platform (injectable `which`, tested) and the install command for what is missing, `lib/hooks/templates.ts` builds the hooks.toml text from that. The sound effects (wav, so every player plays them) live in `apps/api/public/sounds/` and are served at `/config/sounds`; `lib/audio/sounds.ts`'s `syncSounds` downloads what is missing or changed into `<data>/sounds` (`getSoundsDir`), not bundled into the binary, where an external player couldn't open them.
- **Logging**: `lib/logger.ts` is an opt-in JSON-lines file log (`log.warn(message, payload?)`), silent unless both `KAJA_LOG_LEVEL` and `KAJA_LOG_FILE` are set, and never writes to the terminal (Ink owns it). `cli.ts` routes `@kaja/nasi`'s warnings there via `setWarnHandler`.

## CLI surface

- Flags: `--local`, `--cloud`, `--headless`, `-c`/`--continue` and `-s`/`--session <id>` (both `--local` only)
- `telegram` is `--local` only and runs before the LLM config guard (handlers: `lib/telegram/cli.ts`). `--headless` means no Ink render; `telegram` is its only consumer (`kaja --local --headless telegram`, sharing `lib/cli/headless.ts`'s bootstrap with `subcommands/run.tsx`), bare `--headless` exits with an error, and there is no cloud headless yet.
- `login`, `logout`, `config <fetch|paths|diff|wizard>`, `abilities [update]` and `sessions` (lists saved local sessions with the ids `-s` resumes) run before the mode branch. `login`/`logout` are cloud-only concepts (`login` runs `run-cloud.tsx`'s `resolveToken` device login without starting a chat); `config` only touches local files and must never trigger cloud login.
- **`images`** (`subcommands/images.ts`, after the mode is resolved): local mode prints the store's numbers (`lib/store/image-maintenance.ts`'s `localImageStats`, formatted by `lib/image/report.ts`); cloud mode prints the account's from `/stats` with the stored token (no login). `images describe [--retry]` describes images without a description with models.toml's vision model (3 tries, tracked in `nasi_image.describe_attempts`; `--retry` takes the rest), rewriting their labels in saved messages; `images clean [--yes]` finds files without a row, rows without a file and never-saved sessions' images, asks per kind in a TTY (`--yes` doesn't ask, a non-TTY run only reports) and keeps anything under an hour old. Both are local only.
- **Update check** (`lib/cli/update-check.ts`): the compiled binary (not `bun cli.ts`), in a terminal or under `--headless`, reads the latest GitHub release's `manifest.json` on every start (3 s timeout; a failure never blocks). When newer, "Update now?" runs the website's installer into the binary's folder and exits; declining exits in cloud mode (the API only supports the latest TUI) and carries on in local mode. `--headless` only prints the notice, never a prompt (it would keep an unattended Telegram bot from starting).
- **`abilities`**: `kaja abilities update` (`lib/abilities/cli.ts`) sparse-checks-out the source repo's `marketplace/` into a cache (`fetch.ts`, needs `git`) and syncs it into `~/.config/kaja/marketplace/` (`sync.ts`: only files inside its folders; a `.sync-lock.json` of hashes tells untouched copies from your edits; edited files are backed up as `name.bak.ext` before upstream replaces them, which nasi's folder store never reads; files you added are never touched). Bare `kaja abilities` syncs once if never synced, then prints a read-only table (`list.ts`) of each ability's parts, where its MCP server runs, key status and the personas using it; nothing to tick, since every ability loads and personas pick. A cloud user only gets a pointer to https://kaja.io/agent/abilities. `auto-update.ts` fires a non-awaited update at local startup when the lock file is over 24 h old (silent failures, applies next launch). settings.toml `[marketplace]` gates all of it (`url`/`ref` default to GitHub main, or under `KAJA_PROFILE=dev` to the source checkout's branch): `enabled = false` stops everything online, `autoFetch = false` only the startup pull; the wizard asks (`offerMarketplace`).
- **`doctor`** (`subcommands/doctor.ts`, `--local` only): first a keys-and-tokens pass (`runCredentialPass`, which the setup wizard reuses: `lib/doctor/credentials.ts` collects what the config relies on, `checks.ts` tests each live, missing or failing ones are asked through `prompt.tsx` in a TTY, each new value is tested and saved even when it fails (`saved-failing`, so it stays on the to-do list), and unset keys are kept in secrets.toml as commented placeholders), then the models/MCP/tools report, then a summary. A failure's `kind` matters: only `"credential"` (401/403: the service saw the value and refused it) is asked about, while `"unreachable"` (refused connection, 404 for the model) is reported and skipped, because a local server that isn't running needs starting, not a new key. Non-TTY: report only. Result lines are `statusLine` (`lib/doctor/status.tsx`: ink-ui's `StatusMessage` through `renderToString`, so they stay plain `console.log` strings).
- **Tool hosts** (local mode): settings.toml `[tools.hosts]` sends a stdio MCP ability to a sandbox (`"sandbox"`; default `"computer"`). `lib/abilities/sandbox-relay.ts` reaches it through the API's `/sandbox/relay/mcp/<ability>` with the stored cloud token and the ability's secrets.toml key in `X-Kaja-Ability-Key`; signed out, such abilities are refused at once and the chat shows a notice. The wizard and `kaja doctor` run `lib/abilities/hosts.ts`'s `offerAbilityHosts` for each stdio ability a persona uses that can't start here: skip (prints how to install), install uv, get Chrome, or run on a sandbox (not for `localOnly`/`roots` ones).
- **Cloud turns use this computer** (`lib/cloud/computer.ts`): `run-cloud.tsx` opens it in the background (your own abilities, `localOnly`/`roots` ones and stdio ones `[tools.hosts]` sets to `computer`; the file builtins; `run_command` only with `[tools.hosts] shell = "computer"`). `useCloudAgent` sends its declarations with every turn (`clientTools`/`clientSkills`/`clientPersonas`) and on `needs_client_tool` runs each call here (`Computer.run`), asking through the same `ConfirmCommand` gate (`localApproval`; yolo says yes), then resumes with `toolResults`. `clampResult` keeps each within `@kaja/schema/nasi`'s limits and `lib/cloud/turn-body.ts`'s `fitTurnBody` drops the biggest images until the request fits `TURN_BODY_MAX_BYTES`.
- Which shell commands skip approval is `commands.toml` (`lib/config/commands.ts`: `safe` from `kaja config fetch`, the user's `custom` kept across fetches), passed to the agent as `safeCommands`, also by the Telegram bot. Dangerous commands are gated by nasi's `command-risk.ts`.

## First-run wizard

`components/config-wizard.tsx` is the one setup flow: first run (no settings.toml, interactive TTY) and `kaja config wizard`. Dispatch glue is in `lib/cli/`. Non-interactive stdin or `--headless` writes the template untouched, no prompts.

- Steps: language → theme → mode → provider → provider key → server address → extras → each ticked extra's follow-up. A step is skipped when it can't apply (cloud needs no provider; only Ollama and llama.cpp are asked for an address), and `--cloud`/`--local` skip the mode step (a _prefilled_ mode does not: that's the current setting re-offered, so `nextStepAfter` takes the forced mode, not `result.mode`). Language is first and never skipped, and picking one calls `setLanguage` straight away. Every step opens on the current value (`readPrefill`), so Enter throughout keeps a configured machine unchanged.
- Menus (`SelectMenu`, `CheckMenu`) mark the highlighted row with "❯" and bold only, so they read the same before and after a theme is chosen; the whole wizard sits in a `ThemeProvider` that follows the highlight. Providers and extras are checklists (extras start unticked, so one Enter skips them).
- **Keys are typed in the wizard but saved by the credential pass.** The wizard only collects them (no I/O), so a key is always tested before it's saved. `runCredentialPass` takes them as `offered` (`OfferedValues`, keyed by `CredentialItem.where`): a string is tested and saved as if typed, and **`null` means the wizard already asked and was turned down**, so the pass doesn't ask twice. In `WizardResult` that is `""` (shown and skipped) versus `undefined` (never applied); losing the distinction restores the double-ask. `kaja doctor` passes no `offered`. Answer lines say what became of a key (entered / already saved / skipped) but never the value. `applyExtras` also returns items `collectCredentials` can't discover (`telegramItem`: an unsaved token leaves nothing in the config to find).
- No step asks about abilities: every one loads and personas decide. `ensureMarketplace` does the first sync for the wizard and `kaja abilities`.
- `models.toml` is written from the provider catalog (`config/catalog.toml` via `lib/models/catalog.ts`'s `buildModelsToml`) for the ticked providers. `runConfigWizard` first calls `refreshCatalog` (`lib/models/remote-catalog.ts`): the API's `GET /config/catalog` replaces the bundled `CATALOG` (2 s timeout), so a changed default needs no CLI release; any failure (offline, invalid, a `version` other than `CATALOG_VERSION`, a hosted provider not on https since the typed key goes there) keeps the bundled one. The generated examples and `bun check:models` always use the bundled catalog. The wizard does not offer the admin bundle from `GET /config/export` (meaningless to a solo user on a fresh machine); `kaja config fetch`/`diff` still use it.
- `offerModelDownloads` asks once, for the whole list, whether to download the models `models.toml` names that the server hasn't got (`lib/models/pull.ts`: `/api/tags`, then `/api/pull` ndjson). A server that 404s on `/api/tags` is skipped silently; it runs before the credential pass so the provider probe meets a model that is really there.
- The voice step writes one address to `[stt]` as `ws://` (Speaches' realtime WebSocket API) and `[tts]` as `http://`. Config sections are added with `appendTomlSection` (`lib/config/toml.ts`), which appends instead of re-serializing so the templates' commented examples survive and never touches an existing table.
- The Telegram bot's config is secrets.toml's `[telegram]` (`bot_token`, plus the `owner_ids` it saves when someone pairs with the one-time code `lib/telegram/pairing.ts` prints; strangers get silence). The API base URL is `KAJA_API_URL` or the built-in default (`lib/config/api-url.ts`). Geolocation is the marketplace's `geo-service` MCP ability.

## Abilities and personas (local mode)

- `~/.config/kaja/marketplace/abilities/<name>/` holds each ability (synced or your own): any mix of a skill (`SKILL.md`), an HTTP tool (`tool.toml`), an MCP server (`mcp.toml`) and code tools (`tool.ts`, imported on start but only for abilities a persona lists). The folder name is the ability's name; no file carries a `name`, except SKILL.md, whose frontmatter may repeat it as long as it matches. An own MCP server is an ability folder too (there is no own mcp.toml).
- Every valid ability loads; the active persona's `abilities` list decides what a chat gets (nasi's `personaTools`). MCP servers connect only when such a persona is active (`ensureAbilities` → `ensureTools`, with the persona id that picks a roots-taking server's folders); `kaja doctor` connects them all.
- `tools/index.ts`'s `getDefaultTools` builds `@kaja/nasi`'s folder store over `getMarketplaceDir()` and appends `load_skill`, so the TUI and local Telegram both get it; MCP abilities go to `createTools` as `mcpAbilities`.
- HTTP tool abilities use their key from secrets.toml's `[abilities.<name>]` and may reach private hosts. A non-GET one pauses with `confirm_tool`, shown by the same `ConfirmCommand` gate (`kind: "tool"`) and resolved by `use-agent.ts`'s `resolveToolApproval`. Local Telegram answers with a `tool:approve|decline|approve_session:<approvalToken of the call id>` callback; `approve_session` adds the tool's allow key to the session's `grantedTools` (saved with it), and a message instead of a tap skips the call.
- Personas (`marketplace/personas/<id>.toml`) come from `lib/personas/personas.ts`'s `loadPersonas`: `default` first (that file, else the one bundled from repo `marketplace/personas/default.toml`), then the rest by id. Your own skills and personas (those `.sync-lock.json` doesn't record, `ownAbilities`) are tagged `local` by `kaja abilities` and drawn in the accent colour in the picker. Datasets (`marketplace/datasets/<topic>.json`) load through `lib/personas/datasets.ts`.

## Layout

```
cli.ts                  # entry
components/             # Ink UI (layout, inputs, timeline, wizard, …)
hooks/                  # agent, settings, voice, dictation, hooks, …
lib/                    # domain subfolders (cli, agent, auth, config, doctor, models, personas, memory, abilities,
                        # session, store, telegram, audio, mcp, image, markdown); cross-cutting utils at lib/ root
subcommands/            # run.tsx (--local), run-cloud.tsx (cloud), abilities, config, doctor, logout, sessions, telegram
tools/                  # getDefaultTools: wires @kaja/nasi's built-in tools, abilities and MCP for this host
locales/                # en-GB.toml is the source
tests/                  # mirrors the source tree; shared helpers in tests/test-utils.tsx
```

Zod schemas for config/store/domain types live in `@kaja/schema/{config,store,cli}` (see `packages/schema/CLAUDE.md`), not here. Default config templates live at the repo root `config/` (`settings.toml`, and `models.*.toml` generated from `config/catalog.toml` by `bun generate:models`, never edited by hand) and are imported as `../../../../config/...` from `lib/<domain>/*.ts`.

## Conventions

- User-facing strings go through `t()` from `lib/i18n.ts`, with keys added to `locales/en-GB.toml` only (see the root CLAUDE.md)
- Prefer small focused modules under `lib/`, in the domain subfolder they belong to
- Short, explicit TSDoc on non-obvious exports
- Ask first about ambiguous product behaviour, refactors with many call sites, and new tools, personas or provider presets; no feature expansions without discussion
